# shardferry RFC 指南

状态：社区设计流程 v1

这份文档规定 **设计/RFC issue 怎么写、怎么讨论、怎么变成可执行任务**。
它不是功能需求清单，也不是架构决定本身。

## 什么时候需要 RFC

以下变化先用 `design/rfc` issue 讨论，不直接开实现 PR：

- 公共 API、CRD、JSON schema、CLI 语义发生变化；
- readiness、proof、事务或失败语义发生变化；
- 新增 provider、scheduler adapter、运行时边界；
- 修改 source 只读、fail-closed、atomic commit 等安全不变量；
- 跨 Go/Python/Rust/C 边界的职责调整；
- 需要多个模块、多个 release 或外部社区协作的能力。

小的测试补充、文档修正、局部重命名或已批准 RFC 的机械拆解不需要 RFC。

## 十条写作规则

1. **问题先于方案**：先描述谁在什么场景下遇到什么问题，再谈实现。
2. **证据和假设分开**：真实 issue/KEP/复现/测试链接放“证据”，猜测放“假设/未知”。
3. **事实要可复核**：引用具体文件、行号、命令、issue 编号或 KEP 链接。
4. **一个 RFC 只解决一个核心问题**：不要把迁移、调度、存储、UI 混在一份里。
5. **写清当前行为**：现有代码怎么工作，为什么它不够。
6. **写清非目标**：明确这次不解决什么，防止范围膨胀。
7. **列出选项和 trade-off**：至少包含“维持现状”和一种替代方案。
8. **写失败语义**：失败、超时、部分成功、重试和回滚分别发生什么。
9. **写开放问题**：不要假装所有设计已经确定；标出需要 owner/社区决定的问题。
10. **写验收和拆解**：什么条件下算决议完成；哪些部分可以拆成实现 issue。

禁止：

- 编造用户引用、性能数字、社区共识或上游承诺；
- 把尚未验证的能力写成已完成；
- 用“业界最佳实践”代替具体证据；
- 在一个 RFC 中偷偷改变公共契约；
- 把 RFC 做成没有开放问题的营销文档。

## 标准结构

使用 [RFC 模板](RFC-TEMPLATE.zh-CN.md)。最低必须包含：

1. 标题与状态；
2. 问题与真实用户场景；
3. 证据（链接）与假设（明确标注）；
4. 当前行为和代码路径；
5. 目标与非目标；
6. 术语、状态和不变式；
7. 设计选项与取舍；
8. 失败、安全、兼容和运维影响；
9. 开放问题与决策人；
10. 验收标准；
11. 可拆解的实现任务；
12. 参考资料。

## 证据标准

每份 RFC 应至少有一类可复核证据：

- 上游 issue、KEP、PR 或维护者讨论；
- 本地可复现的命令、测试失败或代码路径；
- 真实故障/恢复/迁移记录（脱敏后）；
- 已有实现之间的行为差异。

每条重要结论标注：

| 标记 | 含义 |
|---|---|
| `FACT` | 可从代码、测试或公开链接复核 |
| `REPORT` | 来自用户/issue 报告，尚未独立复现 |
| `ASSUMPTION` | 设计假设，需要后续验证 |
| `OPEN` | 需要 owner 或社区决定 |

## 状态与决策

```text
Draft -> Under discussion -> Accepted / Rejected / Superseded
```

- `Draft`：作者整理问题、证据和选项；
- `Under discussion`：公开征询，维护者收集反证；
- `Accepted`：维护者明确同意方向和边界；
- `Rejected`：记录原因，不删除历史讨论；
- `Superseded`：由新的 RFC 替代，必须链接旧 RFC。

RFC 不会因为“讨论很久”自动通过，也不会由机器人代替 owner 做决定。

## 从 RFC 到实现 issue

RFC 被接受后，才拆实现任务。每个拆解 issue 必须有：

- 单一可合并结果；
- 明确的文件和 API 边界；
- 验收标准和验证命令；
- 依赖关系（如果依赖另一个 issue，写出来）；
- 是否适合 `good first issue`。

不要把所有拆解都标成 `good first issue`。只有满足以下条件才使用：

- 不要求理解完整 RFC 历史；
- 不需要 GPU/K8s/真实多节点；
- 有明确的起始文件和验证方式；
- 不涉及未决议的契约选择。

其他任务使用 `help wanted`、`design/rfc` 或普通实现 issue。

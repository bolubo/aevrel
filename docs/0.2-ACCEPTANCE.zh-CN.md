# shardferry 0.2 — Checkpoint Mobility Control Plane

状态：产品范围草案

## 当前集成状态（2026-10-22）

三块实现已经合入同一集成分支，但还不等于发布门槛全部满足：

| 功能 | 已合并能力 | 当前证据 | 与目标仍有差别 |
|---|---|---|---|
| Kueue preemption | 独立 adapter、strict profile、binary protected/eligible、CPU kind E2E | protected 保持运行；eligible 被抢占；preemptor 正常接入 | 未实现 freshness/cost 排序、restore/fresh-start 区分、grace window、AdmissionCheck StateGate |
| Cross-mesh migration | metadata owner、peer metadata transfer、2D mesh plan、跨 mesh CLI | CPU/torch `2×2 → 3`、128→64 control-plane、source digest 稳定 | 未做真实 4×L20 `4→3`/`4→2`，未做真实 128 rank selector/网络故障注入 |
| Target-ready | Indexed Job 模板、per-rank report、termination message、L3 proof、`target-failed` | Python/Go 单测和集成测试通过 | 未做 Kubeflow TrainJob adapter，未做真实 GPU target Job 的 N-step smoke |

因此当前结论是“0.2 功能集成完成，发布验收未完成”，不是“0.2 已发布”。

`0.2.0` 不做“先上 Live Handoff，再找用户”。它只做三个有上游证据、能组合
成一个真实用户故事的功能：

1. **Checkpoint-aware preemption / restore**：调度器知道 workload 最近的
   完整 checkpoint，并据此做抢占和恢复决策；
2. **Separate-Mesh local-shard migration**：本地分片从一套 DeviceMesh 搬到
   另一套，不要求共享 checkpoint 目录；
3. **Target-ready integration**：迁移后目标 Job 真的加载并继续运行，而不是
   文件存在就算成功。

Live Handoff 是后续高阶模式，不是 0.2 的发布门槛。

## 用户故事

Kueue/Kubernetes 训练平台里有一个低优先级任务：

- 刚写完一个完整 checkpoint；
- shard 分散在多台机器的本地 NVMe；
- 平台需要给更高优先级任务腾 GPU；
- target 集群/队列的卡数不同；
- 平台希望任务不是被盲目杀掉，而是知道 checkpoint 状态后选择：
  - 直接重启；
  - 从最近 checkpoint 恢复；
  - 将状态迁移到另一套拓扑后继续。

0.2 的结果：

```text
Kueue sees workload checkpoint state
        -> choose preemption/restore policy
        -> shardferry migrates local shards to target mesh
        -> target Job loads DCP and runs N steps
        -> status/proof says target is actually ready
```

## 共享内核：CheckpointState

三个功能共享一个状态契约，不是三个互不相关的小工具。

`CheckpointState` 至少描述：

- source workload / job / namespace / uid；
- latest complete version 和 step；
- checkpoint 格式和 provider；
- source mesh、ranks 和本地分片位置；
- 完成时间和 freshness；
- target mesh 和目标 rank 数；
- restore / migrate / restart 的可行性；
- target-ready 结果和 proof。

## 功能 1：Checkpoint-aware preemption / restore

### 用户问题

调度器只知道优先级和资源，不知道“刚 checkpoint 的任务踢掉代价小”还是
“训练三小时还没 checkpoint 的任务踢掉代价大”。

### 交付

- 独立 `shardferry-kueue-adapter`，不改 Kueue 源码；
- 可选 `AdmissionCheck` StateGate，对训练 Job 做 admit/delay/reject；
- controller 监听训练 Job 的 checkpoint 完成事件；
- 发布 checkpoint freshness/complete/step 信息；
- 使用 Kueue `PreemptionConfig` 的 numeric-label 规则接入候选选择；
- 显式区分 `restore-from-checkpoint` 和 `start-fresh`；
- preemption 前支持有限的 checkpoint grace window；
- Kueue 不直接依赖 shardferry 的数据面。

### 验收

- checkpoint 新鲜的任务被优先保留；
- 没有完整 checkpoint 的任务不会被过期标记误判为可恢复；
- Kueue 抢占候选能读到 freshness/cost 信号；
- 抢占后 Workload 状态能区分 restore 和 fresh start；
- 失效、重复、过期 checkpoint 有明确 condition。

## 功能 2：Separate-Mesh local-shard migration

### 用户问题

DCP 的 load-time reshard 仍依赖可读取的 checkpoint storage；本地 shard
分布在 source 机器上，target 不共享该目录，且 source/target DeviceMesh
不同。

### 交付

- MigrationSpec 显式表达 source mesh、target mesh 和 placements；
- 从本地 shard metadata 生成跨 mesh plan；
- `metadataOwnerRank` 只由 owner 读取 `.metadata`，再通过 source agent 的
  metadata transfer API 分发给 peer agents；不要求所有 source 节点挂同一个
  checkpoint 目录；
- 不要求全局 NFS/S3 或 full gather；
- source 只读、journal 续跑、target DCP atomic commit；
- 先支持 1D world-size，复杂 TP/PP 不承诺；
- `shardferryctl` 从一份 YAML 创建并等待迁移。

### 验收

- 4×L20 上完成 `4→3` 或 `4→2` 的真实 DCP；
- CPU/控制面完成 `128→64`；
- source SHA256 前后不变；
- target rank load smoke 通过；
- 任何 rank 失败不能报告整体成功。

当前本地证据（2026-10-22，CPU + torch 2.14.1+cpu）：

- `2×2 → 3` 的真实 DCP local-shard 迁移通过；
- 两个独立 source agent 模拟 owner/peer：peer 没有 `.metadata`，安装 owner
  metadata 后完成 inventory、跨 mesh plan、apply 和 target load；
- 128 source / 2D mesh → 64 target / 2D mesh 的 control-plane plan 通过；
- full gather 保持关闭，source digest 前后一致。

仍未覆盖：真实 4×L20 的双机 metadata-owner 路径、128 节点物理 selector
端到端，以及复杂 TP/PP。

## 功能 3：Target-ready integration

### 用户问题

checkpoint 写完不代表恢复成功。平台需要知道 target `TrainJob`/Job 是否真的
加载了模型、优化器并能继续运行。

### 交付

- 通用 Kubernetes Job validation hook；
- 可选 Kubeflow `TrainJob` adapter；
- target 加载迁移后的 DCP，至少运行 N 个训练 step；
- 输出 `target-ready` condition、version/step、耗时和 proof；
- 如果 dataloader/RNG/scheduler 未保存，报告明确标记“状态不完整”；
- 失败时区分“文件迁移成功”和“target 可训练失败”。

### 验收

- `target-ready=True` 仅在真实加载和 N step 成功后设置；
- target Job 使用的 world size 与迁移后的 DCP 匹配；
- target Job 失败不能把 migration 标记为 succeeded；
- `shardferryctl describe` 和 proof 能看到结果。

### 实现状态（2026-10-22）

- 已实现通用 Indexed Job adapter、per-rank report 契约、Pod termination
  message 收集、controller 重启恢复和 `TargetReady` status/proof；
- 详细接入见 [Target-ready 契约](TARGET-READY.zh-CN.md)；
- 仍未实现 kubeflow TrainerJob 薄 adapter，不阻塞 0.2 的 L3 验收。

## 0.2 的演示

不是“同机复制更快”，而是：

```text
Kueue needs GPUs
  -> preempts workload A based on checkpoint freshness
  -> shardferry moves A's local shards to cluster B (different world size)
  -> target Job loads DCP and runs
  -> proof: time_to_first_step, steps_lost, bytes_moved
```

报告必须包含：

- preemption decision 依据；
- checkpoint version/step；
- time-to-target-first-step；
- steps lost / replayed；
- bytes moved；
- target continue steps；
- source digest、target load、proof。

## 明确不做

- CUDA context / Python 进程内存热迁移；
- CRIU/cuda-checkpoint 透明进程恢复；
- Live Handoff（放到后续版本）；
- 任意 TP/PP 重排；
- 没有 checkpoint state 的自动猜想；
- 所有训练框架一次性支持；
- 生产 SLA 或“所有场景都能迁”的承诺。

## 发布门槛

1. 三个功能都有真实用户场景或等价端到端 PoC；
2. Kueue 集成在 kind 或小集群跑通；
3. 4×L20 完成一次跨 mesh local-shard migration；
4. target Job 继续运行 N 个 step；
5. source 不变、失败可恢复、proof 可验证；
6. 文档明确说明 0.2 不是 Live Handoff。

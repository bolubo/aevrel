# shardferry 0.2 — Live Handoff 目标与验收

状态：设计阶段
主题：**训练热接力（Live Handoff）**

0.1 解决的是“把一个已经结束的 checkpoint 搬到目标拓扑”。0.2 要解决的是：

> source 训练任务还在产生 checkpoint，target 已经准备好一份可接管的状态；
> 在明确的 checkpoint 边界暂停 source，把最后增量交给 target，让 target
> 从同一个版本继续训练。

这不是进程级迁移，不搬运 CUDA context 或 Python 进程内存。0.2 的准确定义是
**checkpoint-consistent handoff**：source 和 target 在同一个已完整写入的
checkpoint 边界交接。

## 1. 用户故事

一个 128-rank 训练任务在 source 集群运行，checkpoint 分散在本地 NVMe：

- source 集群需要缩容、升级或被回收；
- target 只有 64 张卡；
- 没有可挂载到 target 的全局 checkpoint 目录；
- 用户不想等下一次从零启动，也不想丢失最后一个 checkpoint 之前的进度；
- target 必须证明模型、优化器和目标训练循环真的可以继续。

用户期望：

```bash
shardferryctl handoff -f handoff.yaml
```

最终看到：

- source 在某个 checkpoint version/step 暂停；
- target 已追赶到该版本；
- target 完成 target DCP load；
- target 训练循环继续运行 N 个 step；
- source 可以安全停止；
- cutover 失败时 source 可以恢复；
- 全过程有 timeline 和 migration proof。

## 2. 0.2 的范围

### 包含

- source 侧 checkpoint 版本发现和增量 follower；
- target 侧不同 world size 的 shadow 状态；
- checkpoint barrier、fence、pause、final delta、promote、rollback；
- target training harness 的加载和继续运行验证；
- `shardferryctl handoff` 和状态/时间线；
- 失败恢复、重复 handoff、stale fence、promote 失败的明确状态；
- 1D world-size resharding 的真实 GPU 验证；
- 128→64 的控制面/数据面规模验证；
- cutover pause、RPO、重传字节、target load 的证据。

### 不包含

- CUDA context、Python 堆、进程内存和连接状态的在线迁移；
- 任意 tensor/pipeline parallel 布局的自动重建；
- dataloader/RNG/scheduler 未写入 checkpoint 时的严格同轨迹恢复；
- 多 source 同时写同一 checkpoint 的并发一致性；
- 自动发现所有训练框架并自动注入 checkpoint hook；
- 生产 SLA、跨公网任意网络条件下的 RTO 承诺。

0.2 只支持显式 checkpoint 版本协议和文档中声明的 placement。

## 3. 关键定义

| 名称 | 定义 |
|---|---|
| checkpoint boundary | source 已完整写入 manifest 的一个 version |
| follower | 持续把已提交 source version 追赶到 target shadow 的后台任务 |
| handoff | source 暂停、target final catch-up、promote 和 target 继续的完整事务 |
| RPO | 允许回退到最近完整 checkpoint 的最大版本数/step 数 |
| pause budget | source 从暂停到 target 可继续的最大时间 |
| target ready | target DCP load 成功，目标训练循环至少运行指定 step |

0.2 的默认 RPO 是 **一个 checkpoint interval**，除非用户的训练程序把更细粒度
状态写入 checkpoint。不能把“模型加载成功”宣传成“训练完全无感”。

## 4. 验收门槛

以下全部是 0.2 发布门槛。

### A. Source 训练与版本协议

- [ ] 提供一个可复现训练 harness，source 以固定间隔产生完整 DCP version；
- [ ] version 包含 job uid、step、parent、metadata hash 和 complete marker；
- [ ] source 在 follower 追赶期间持续写新版本；
- [ ] source checkpoint 文件树只读语义不变；
- [ ] source 可以在 handoff 失败后继续写 checkpoint。

### B. Target shadow 与不同拓扑

- [ ] target follower 使用不同 world size（至少 `4→3`，CPU 规模 `128→64`）；
- [ ] shadow 不产生 full gather，不要求全局 S3/NFS；
- [ ] target 追赶到最新完整 version 后，状态可查询；
- [ ] target follower 重启后继续追赶，不重复已完成 chunk；
- [ ] follower 落后、失败、磁盘不足时，handoff 不误报 ready。

### C. Cutover 事务

- [ ] source 只在 checkpoint boundary 暂停；
- [ ] pause 有明确预算和计时；
- [ ] final delta 完成前 target 不能 promote；
- [ ] fence/epoch 阻止 source 和 target 同时训练；
- [ ] target promote 成功后才允许 source 被标记为可停止；
- [ ] cutover 失败可以 rollback，source 恢复；
- [ ] stale fence、重复 handoff、promote 取消都有明确错误码。

### D. Target ready

- [ ] target 模型和优化器可以从迁移后的 DCP 加载；
- [ ] target 训练循环从指定 version/step 继续至少 N 个 step；
- [ ] 输出/ loss 与参照训练在文档规定的容差内；
- [ ] 如果 dataloader/RNG/scheduler 未保存，报告必须明确标注；
- [ ] target ready 失败不能报告 handoff 成功。

### E. 真实 GPU

- [ ] 4×L20 上完成一次 `4→3` 或 `4→2` 的 live handoff；
- [ ] source 继续训练期间 target shadow 能追赶到最新版本；
- [ ] cutover 后 target 完成真实模型/优化器加载并继续训练；
- [ ] source checkpoint 在 handoff 前后 SHA256 不变；
- [ ] 记录 pause、RPO、传输字节、target load 时间。

### F. 规模与失败矩阵

- [ ] 128→64 CPU/控制面规模验证；
- [ ] source follower 失败；
- [ ] target agent 在 staging/commit 中失败；
- [ ] controller 在 handoff 中重启；
- [ ] final delta 失败；
- [ ] promote 失败并 rollback；
- [ ] source 在失败后恢复训练。

### G. 产品输出

- [ ] `shardferryctl handoff -f FILE`；
- [ ] `shardferryctl describe handoff NAME --timeline`；
- [ ] `status` 显示 version、step、follower lag、pause、fence、target ready；
- [ ] `proof` 可独立验证；
- [ ] README 和 release notes 不把未验证情形写成生产承诺。

## 5. 性能与证据口径

0.2 不以同机 raw-copy 速度作为主卖点，必须报告：

- target shadow 首次追赶时间；
- 后续版本增量字节比例；
- cutover pause；
- RPO（版本数和 step）；
- target load 时间和 target job 成功 step 数；
- failure 后重传字节；
- 峰值 host RAM、target disk amplification。

建议门槛（不是生产 SLA）：

- pause 在配置预算内；
- RPO 不超过配置 checkpoint interval；
- 90% 中断后不重传已提交 chunk；
- target 8/8 或 64/64 load 后，目标训练 loop 至少继续 10 个 step。

## 6. 验证矩阵

| 层级 | 验证 |
|---|---|
| 单元 | follower、fence、version、pause、rollback、promote |
| 本地集成 | source version 流 + target shadow + handoff |
| 4×L20 GPU | model/optimizer/forward + target continue steps |
| 两套 kind | 16→8 控制面 + 故障注入 |
| 规模 | 128→64 CPU/synthetic |
| 证据 | timeline、proof、pause/RPO、source digest |

## 7. 发布定义

0.2 发布需要：

1. 上述 A–G 全部门槛通过；
2. 至少一条真实 GPU live handoff 证据；
3. source/target 不在同一控制域也能完成（kind 或等价测试环境）；
4. 失败矩阵和 rollback 有日志；
5. release notes 明确 0.2 是 checkpoint-consistent，不是进程 live migration；
6. 生成 `v0.2.0` tag、wheel、镜像、Helm chart 和证据包。

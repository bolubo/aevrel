# 迁移品类：跨控制域的状态与工作负载迁移

日期：2026-10-22
状态：品类定义；不是 0.2 的交付承诺

## 一句话

shardferry 的长期品类不是“Checkpoint 迁移工具”，而是跨控制域迁移层：

> A 有、B 缺；判断能不能迁，选择最快且安全的路径，执行迁移，并证明 B
> 真正可用。

“集群”是用户最直观的说法；更准确的边界是不同控制域。A/B 可以是两个
Kubernetes、云上云下、本地多集群，或单机到集群。同集群内交给
Kubernetes/CSI；A/B 都有且持续同步的主从/双活不是迁移。

## 两个核心判据

一条迁移成立，至少满足：

1. A/B 属于不同控制域；
2. A 有所需的工作负载或状态，B 缺；
3. 目标环境具备承载能力，或能明确报告不可迁的阻塞项。

“B 缺”可以是三种情况：

| 缺口 | 迁移对象 | 是否要搬数据 |
|---|---|---|
| B 已有数据，只缺服务 | manifests、镜像、配置、依赖、接线 | 否 |
| B 已有服务，只缺状态 | 文件、DCP checkpoint、volume、dataset | 是 |
| B 服务和状态都缺 | 工作负载定义 + 状态，按依赖顺序 | 是 |

如果 B 已经有服务和数据，且两边持续双写、主从复制或 CDC，那是复制/联邦，
不是迁移。

通用迁移工具不承诺重写应用本身。B 的 CPU 架构、GPU 驱动、依赖版本或权限
不满足时，工具应该给出明确的不可迁原因和改造项，而不是把“能启动”当成
“迁移成功”。

## 四个核心问题

通用迁移不是单纯的字节搬运，而是一个“迁移编译”问题：

1. **能不能迁**：盘点 A 的状态和依赖，检查 B 的承载能力、兼容性和权限；
2. **迁什么**：找出工作负载、数据、配置和依赖的闭包，区分缺失与已满足；
3. **怎么迁最快、最安全**：根据网络、磁盘、拓扑、停机窗口和成本生成计划；
4. **怎么证明迁成功**：用 bitwise、load smoke、依赖检查和 cutover 语义验证。

数据搬运只是第 3 步的一种后端。真正的产品壁垒在判定、计划、事务边界和
验证证据，而不是“能发 HTTP range 请求”。

内部统一表示应该是一张 migration graph：节点是 workload、image、config、
secret、volume、database、checkpoint、network、IAM 等资源，边是依赖、
顺序和一致性约束。provider 只负责实现某类节点的能力，planner 在这张图上
做判定和全局优化。

## 集成而不是替代

这个品类最容易做错的方向，是把自己做成“万能搬运器”，结果和每个厂商的
数据面正面竞争。正确方向是迁移控制面：

- DCP / nvRX 负责 checkpoint 语义和拓扑转换；
- CSI snapshot / Portworx / 云盘负责卷快照和块复制；
- Velero 负责 Kubernetes 资源备份恢复；
- 对象存储 / rclone 负责对象和文件传输；
- 数据库、消息队列的原生工具负责一致性复制；
- 云 API 负责镜像、网络、IAM 和目标资源。

shardferry 不重写这些后端，而是把它们纳入统一的 provider contract，
由 planner 选择、组合和排序。每接一个 provider，能力是叠加的，不是把
核心状态机重写一遍。

provider contract 至少需要描述：能力、发现、成本估计、执行、状态、验证、
幂等和回滚。没有这层契约，所谓“通用”最后会退化成一堆 if/else。

## 上层控制面，底层可替换

默认位置是上层控制面和迁移语义，不把通用数据面吞吐作为主卖点。底层谁做得
好就用谁；只有 provider 无法表达语义、无法满足正确性/恢复/SLO，或者没有
稳定 API 时，才进入自研评估。

满足以下任一条，才值得自己写：

- provider 没有稳定 API 或生命周期接口；
- API 无法表达拓扑、事务、一致性、验证等关键语义；
- 失败后无法恢复/回滚，或错误不可判；
- 是关键路径，现有 provider 达不到用户 SLO；
- 安全/合规要求不能把数据或控制权交给第三方。

优先集成：

- CSI/云盘快照、Velero、数据库/队列原生复制、对象存储、镜像仓库；
- 云 IAM/网络、Kubernetes RBAC、Prometheus/OpenTelemetry；
- 这些是成熟能力，重复实现只会增加维护面。

适配层不是造轮子：如果 provider 的 API 可用但错误、观测或语义不统一，
写 adapter 和错误归一化层是合理的。

当前分类：

- 自己做：migration graph、planner、统一错误模型、验证/commit、DCP 语义、
  local-disk 状态迁移、Kubernetes 控制面；
- 集成：CSI/Velero/数据库原生/云 API/registry/auth/observability；
- 暂不做：通用高性能文件传输、分布式文件系统、VPN/overlay、服务网格、
  调度器、数据库、备份系统；
- 可选实验：Rust 零拷贝 DCP 数据面，只作为可替换 provider，不作为产品身份。

## 问题自研，不等于实现全自研

自研边界应该落在“现有厂商/大项目没有解决，而且用户能感知到差异”的问题上，
而不是每一行内部实现。整体问题定义、迁移不变量和解决方案是我们的；内部
组件能复用成熟实现就复用。

以 128-rank local-disk DCP 迁移为例：

- **必须自研**：跨节点 shard 发现、源/目标拓扑规划、无全局汇总的传输编排、
  staging/commit barrier、幂等和续跑、跨层错误模型、target DCP 可加载验证；
- **优先复用**：PyTorch DCP 的元数据/加载语义、HTTP/序列化框架、压缩/校验库、
  Kubernetes controller-runtime、TLS/RBAC、日志/指标、Helm；
- **不复用也不自研**：网络协议栈、分布式文件系统、调度器、数据库、通用对象
  存储、通用备份系统——这些要么直接集成，要么明确不做。

复用要放在 provider/adapter 后面，不能让第三方类型、错误和生命周期渗透到
核心状态机。这样以后换实现不会重写迁移语义。

判断一个内部实现要不要自研，只看几个问题：

1. 它是否决定用户可见的正确性、恢复能力、性能或安全边界？
2. 现有 provider 是否有稳定 API，语义是否足够表达迁移约束？
3. 复用是否把关键失败路径交给不可控组件？
4. 自研的维护成本是否明显低于它带来的差异化和风险降低？

前三个问题只要有一个是硬缺口，就进入自研评估；否则默认复用。不是因为
“自己能写”就写，也不是因为“开源有”就无脑接。

## 综合最优与通用判错

“综合最优”不是单点吞吐最大，而是在用户约束下选择可解释的 Pareto 方案：

- 完成时间 / time-to-ready；
- 停机窗口；
- 传输字节、带宽和云出网成本；
- 一致性等级；
- 失败风险；
- 回滚成本。

同一批迁移对象可能有多种路径：全量 vs 增量、快照 vs 文件扫描、并行 vs
串行、先迁数据 vs 先起服务。优化目标是全局关键路径，不是每个 provider
各自最快。某个数据库恢复如果卡住，单独把文件复制再快也没有意义。

“通用判错”需要统一错误模型：错误属于哪一层、哪个资源、是否可重试、
当前一致性状态、允许的动作（继续/重试/回滚/人工介入）。否则接的
provider 越多，用户越难知道失败到底发生在哪一层。

## 为什么先做 DCP

DCP 是当前最好的第一垂直场景，不是品类上限：

- 用户痛点真实：训练任务、节点回收、集群替换和扩缩容都会遇到；
- 约束足够硬：local disk、超大对象、拓扑变化、不能全量汇总；
- 正确性可验证：bitwise、target DCP load smoke；
- 有明确失败语义：staging、commit barrier、resume、repair；
- 能逼出通用内核：状态发现、拓扑规划、传输、转换、验证和事务提交。

如果先做通用文件拷贝，我们会直接面对 rsync/rclone/对象存储和云厂商的
红海，且没有足够硬的差异化。先把 DCP 打穿，再把内核抽象成 provider，
比一开始做“万能迁移”更可信。

## 为什么这个品类没有单一霸主

不是完全没人做，而是市场被拆成了多个相邻品类，每个只覆盖一段：

| 层 | 代表能力 | 默认假设 | 留下的缺口 |
|---|---|---|---|
| 备份/恢复 | Velero、Kasten、Commvault | 恢复到原环境或相似环境 | 跨控制域语义迁移、目标拓扑转换 |
| 存储/卷 | CSI snapshot、Portworx、NetApp | 卷可见、可复制 | local-disk 发现、跨集群编排、应用级验证 |
| 云迁移 | AWS MGN、Azure Migrate、Google Migrate to Containers | 迁入本云 | 中立、跨云、Kubernetes 状态迁移 |
| 多集群编排 | Karmada、Cluster API | 应用已经可部署 | 工作负载和状态的实际搬运 |
| 数据库/中间件 | 原生备份、复制、CDC | 数据层自己管理一致性 | 跨层依赖顺序、应用级 cutover |
| AI checkpoint | DCP、nvRX、单机 reshard 工具 | 同 world 或全局路径可见 | local-disk、跨集群、事务和验证 |

没有一个中立产品从“A 有 B 缺，能不能迁，怎么迁，迁完怎么证明”这个整体
问题出发。原因主要有六个：

1. **迁移是一次性项目，不是高频操作。** 客户更愿意买咨询、云厂商迁移
   服务或存储厂商的复制能力，而不是长期订阅一个通用工具。
2. **“能不能迁”是语义问题。** Kubernetes manifest 只描述部署，不描述
   应用真实状态、事务边界和隐式依赖；通用工具必须做静态分析、运行时
   发现和人工确认。
3. **环境长尾极长。** K8s 发行版、CSI/CNI、云 IAM、操作系统、GPU 驱动、
   镜像仓库、网络策略和安全边界都会改变迁移方案。
4. **正确性和回滚风险高。** 服务起来不等于状态正确；数据一致性、停机
   窗口、cutover 和 rollback 都需要产品级语义，不能靠脚本。
5. **厂商激励不一致。** 云厂商希望数据迁入，存储厂商希望绑定自己的存储，
   备份厂商希望恢复回原平台；中立迁移层天然缺少“把数据送走”的动力。
6. **性能是多目标优化。** 字节数、并发、拓扑、压缩、去重、停机时间和
   成本互相冲突，很难用一个通用 benchmark 说服所有用户。

所以真正的空白不是“再写一个拷贝工具”，而是“迁移判定 + 迁移编译 +
执行 + 验证”的整体层。这个层做出来后，下面的传输后端可以替换，上面的
工作负载类型可以增加。

## 产品演进

- 当前：DCP state provider，先把 local-disk checkpoint 迁移打穿；
- 下一步：通用 state provider，覆盖文件、volume、dataset 和 artifact；
- 再下一步：workload provider，覆盖 manifests、镜像、配置、依赖和接线；
- 更远：跨异构控制域的迁移判定、计划优化、cutover 和回滚；
- North Star：一种迁移单元，任意控制域，完成后有可验证证据。

控制面可以以 Kubernetes operator 为第一形态，但内核状态机不能绑死
Kubernetes、DCP 或 AI。否则品类一扩大，整个实现就要重写。

## 与 etcd 的关系

etcd 的类比应理解成“角色”，不是“位置”。shardferry 不会成为 Kubernetes
核心组件；更现实的目标是成为 AI 平台和集群发行版默认集成的迁移层，
用户安装平台时就带有，通过 operator、CRD 或 SDK 调用。

要接近这种默认能力，关键不是功能数量，而是：

- API 和错误语义稳定；
- 失败可恢复、不可静默成功；
- 迁移结果可验证、可审计；
- 安装和接入成本足够低；
- 对真实用户最重要的垂直场景先做到无可替代。

## 不做什么

- 不做同集群内的 Pod/卷重调度；
- 不做 A/B 双活、持续主从复制和 CDC；
- 不替代数据库、消息队列自己的复制协议；
- 不承诺所有应用都能迁移，不重写应用；
- 不把“备份可恢复”直接等同于“迁移可验证”；
- 不在 0.2 中交付通用 workload provider。
